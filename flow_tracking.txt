1. Registration
participant_login.tsx → starter1.tsx → "New User?" opens RegisterSheet.tsx (modal, doesn't navigate away) → useRegisterForm.ts → registerTrainee() in auth.ts → POST /trainees/register → trainee.py:register_trainee → Trainee model → trainee table, status='Pending'.

Note: src/app/new_trainee.tsx is a different, admin-only screen (trainer adds a trainee) — not this path.

2. Login
starter1.tsx → loginTrainee(phone) → POST /trainees/login (phone lookup only, no password/OTP check) → JWT issued → session held in useAuth.tsx's React state — no AsyncStorage/SecureStore anywhere, so the session is lost on reload.

3. Joining a session
session.tsx → useSessionScreen.ts → GET /sessions/current → _select_current_conference() in session.py. This is hardcoded to DEMO_TRAINER_EMPLOYEE_ID = "demotrainer" — every trainee always lands on that one trainer's conference; there's no real "pick a session" flow yet (comment says QR/trainer-ID entry is planned but not built).

4. Attendance
secure_checkin.tsx → attendance.tsx. Backend has three endpoints (verify-location, check-in, check-in/secure), but only the plain POST /attendance/check-in (no location, no photo) is actually reachable — useSecureCheckIn.ts defaults to "entry mode," which discards the captured photo and never calls the geofenced/secure endpoint. So all that camera/location UI doesn't currently write anything to the DB.

5. Session flow (Standard Test / Live Quiz / Survey)
Module sequencing lives in module_flow.py (ATTENDANCE → STANDARD_TEST → LIVE_QUIZ → SURVEY), driven by conference.sessionConfig. useTraineeHome.ts polls GET /sessions/current every 10s. Entering the Live Quiz goes through wait.tsx, which is a fixed 5s setTimeout fake wait screen with hardcoded fallback demo IDs — it doesn't actually poll for anything. Once in useQuiz.ts, questions are fetched upfront and paced client-side; the per-question "Correct/Incorrect" feedback is fake too (compares against a hardcoded "A" fallback since the backend deliberately never sends the answer key) — only the final backend-scored submission is real.

6. Proctoring
Fully on-device now via ML Kit (ProctoringEngine.ts) → OnDeviceProctoringPanel.tsx → feeds usePostTest.ts. Violations are tracked only in-memory (violations.ts) — not persisted anywhere. The old backend /proctoring/check-frame endpoint is orphaned (no frontend caller left, pre-dates the ML Kit migration). A security-violation lockout never reaches the backend either — terminateAssessmentWithViolation() is permanently routed to the mock service.

7. Assessment submission
submitAssessment() → POST /assessments/{suite_uid}/submit → assessment.py scores against Question.correct_answer, writes an Assessment row per answer + one AssessmentResult row. Same endpoint/tables for Standard Test, Live Quiz, and Survey — a "Survey" is just an AssessmentSuite with a different assessment_type.

8. Completion
No explicit "finished" endpoint — completion is derived: GET /sessions/current marks each module isCompleted from Attendance/AssessmentResult rows, and polling stops once all modules are done. GET /sessions/history is the real durable record of a finished session; a lot of the in-between UI (durations like "Ran : 45m 3s", scores shown right after a test) is patched client-side from navigation params rather than re-derived from the server.

Biggest issues, if you want to tackle any next (same "hardcoded/fake" pattern as the trainer dashboard work): the hardcoded demo-trainer session lookup (#3) is the most consequential — no trainee flow works correctly beyond that one demo conference until session selection is built. After that: the discarded secure-checkin photo/location (#4), and the fake live-quiz wait screen (#5).


## Trainer flow

1. Trainer login
trainer_login.tsx → useTrainerLogin.ts → loginAdmin() in admin.ts → POST /admin/login → admin.py:login, which checks the admin table first and falls back to the agencyteam table (since real trainers live there, not in admin) → issues a JWT whose subject is prefixed admin: or agencyteam: → returns { access_token, admin: { username, name, role } }, stored via setAdminSession into useAuth.tsx's adminSession state — the same session slot trainer and admin both use. The role string in the response drives client-side routing only: "admin" → /admin_dashboard, "trainer" → /trainer_dashboard, anything else shows "This account doesn't have access here yet." Like the trainee session, nothing is persisted to AsyncStorage/SecureStore, so a reload logs the trainer out.

2. Trainer dashboard / agenda
trainer_dashboard.tsx → useTrainerDashboardScreen.ts → fetchTrainerAgenda() in training.ts → GET /admin/trainings?start=&end= → training.py:list_trainer_trainings, scoped to Conference.trainerEmployeeId == admin.username and ordered by timestamp desc. The hook actually fires two independent copies of this call: one scoped to whatever date range the trainer picked (feeds the agenda/recent-sessions cards) and a second hardcoded to rangeForPreset("this_month") purely for the Training Efficiency card. Both are refetched every 10 seconds via a silent background setInterval inside useFocusEffect, the same polling cadence as the trainee home screen. All the stats (totalTrainees, completed/pending counts, percentages) are computed client-side in dashboardUtils.ts's calculateDashboardStats — notably totalTrainees is just a naive sum of parseInt(batchSize) across agenda items, not a real headcount. Tapping a session calls handleLaunch(conferenceUid) → router.push("/session_dashboard").

3. Creating a training session
add_training.tsx → useAddTrainingForm.ts. On mount it loads fetchAssessmentSuites() (GET /admin/assessment-suites), fetchTrainers() (GET /admin/trainers → trainer.py:list_trainers, deduped Admin+AgencyTeam rows with role=="trainer"), and fetchChecklistItems() (GET /admin/checklist-items); picking a district re-fetches fetchVenues(district) (GET /admin/venues?district=). All four are real, newly-added endpoints (routers/catalog.py, routers/trainer.py) backed by the new Category/SubCategory/Venue models — genuinely wired, not mocked. Submitting builds a sessionFlow object (an attendance config plus up to three ModuleConfig entries for standardTest/liveQuiz/survey — category, assessmentSuiteUid, startTime/endTime, unlockCondition) after client-side validateModuleSequence() checks each enabled module's window doesn't overlap the previous one, then posts via createTraining() → POST /admin/trainings → training.py:create_training. That handler serializes sessionFlow into a JSON sessionConfig blob on the new Conference row, and separately copies the chosen Standard Test's and Survey's assessmentSuiteUid out into dedicated postAssessmentUid/surveyUid columns — necessary because the trainee-facing session.py never reads sessionConfig, only those two columns. The row is created with conferenceStatus="Scheduled" and status="Pending": every new training needs an admin's approval (see next section) before the trainer can start it.

4. Training approval
This is an admin-role action, not something pending_trainings.tsx does, despite its name. admin_dashboard.tsx → useAdminDashboard.ts calls fetchPendingTrainings() → GET /admin/trainings/pending → training.py:list_pending_trainings (require_admin_role-gated, returns every trainer's Conference rows with status=="Pending" org-wide), and handleApprove/handleReject → approveTraining()/rejectTraining() → POST /admin/trainings/{uid}/approve or /reject → training.py:approve_training/reject_training, which just flip conference.status to "Approved"/"Rejected" and stamp updatedBy. The trainer-side pending_trainings.tsx screen instead calls useTrainerAgendaList(true), which re-fetches the trainer's own GET /admin/trainings feed and filters client-side for approvalStatus === "Pending" — it shares TrainingListView.tsx with the unfiltered training_list.tsx and has no approve/reject controls at all. So a trainer can see which of their own sessions are still awaiting review, but the actual approve/reject decision only happens on the admin dashboard.

5. Running a live session
session_dashboard.tsx → useSessionDashboardScreen.ts. Note the conferenceUid falls back to a hardcoded "CONF25456581" whenever no param is passed (params.conferenceUid || "CONF25456581") — the same style of baked-in demo ID the trainee-flow doc calls out for session.py's DEMO_TRAINER_EMPLOYEE_ID. loadData() polls fetchSessionDashboard() → GET /admin/trainings/{uid} → training.py:get_session_dashboard (owner-scoped to the trainer's own conference) every 5 seconds — tighter than the dashboard's 10s. That endpoint calls auto_advance_if_due() (services/module_flow.py) on every fetch, then assembles audience/assessment/topPerformers/trainees/executionFlow/auditLog from real Attendance/AssessmentResult/ConferenceActivityLog rows. handleStartSession() → startTraining() → POST .../start → training.py:start_training, which 403s unless status=="Approved", flips conferenceStatus to "Ongoing", and activates the first configured module (logging a STARTED row). handleEndSession() → endTraining() → POST .../end → training.py:end_training, closing the active module (STOPPED) and flipping conferenceStatus to "Completed". That's where real wiring stops, though — almost everything else in the control room is decorative. RuntimeAndQuizSection's SessionRuntimeCard is entirely hardcoded ("4h 42m 46s" actualRuntime, 92% consumed, 50% module completion — literal props, ignoring data.runtimeSeconds), and its ActiveQuizModuleCard is likewise hardcoded (a fixed "01:20:47" timer, "Targeted 24 QPs") apart from the activeModuleId label and the "End Quiz" button, which is the only one of the three that's real (it calls the genuine endTraining()). LiveStudioSection renders LiveStudioCard with onLaunchNext, onStopTimer, and onLobby all bound to () => {} — and there's no backend endpoint at all for broadcasting a live-quiz question, so this control couldn't do anything real even if wired up. The same section renders ParticipantAttendanceCard with no participants prop and no onUnlock prop, so the entire "Participant Master List" — who's shown, their PRESENT/ABSENT status, and the suspicious-activity lock — comes from the component's own hardcoded DEFAULT_PARTICIPANTS array, completely unrelated to the real data.trainees the dashboard already fetched. Its onCheck/onReject icons are wired to () => {} too, meaning they never call the fully-implemented markAttendance()/resetAttendance() (POST/DELETE /admin/trainings/{uid}/attendance/{trainee_uid}) that exist in api/training.ts and work correctly on the backend — that manual-attendance-override endpoint is real, it's just never invoked from this screen. SuspiciousActivityModal and UnlockExamModal sit on top of that same fake data: the lock only ever appears for one hardcoded demo trainee ("ANAND RAI") whose proctoring.flags/logs are baked into DEFAULT_PARTICIPANTS, and confirming an "unlock" just adds the id to a local unlockedIds React state Set — nothing reaches the backend, and there's no backend concept of a proctoring lock on a conference/trainee to begin with (this is the trainer-side mirror of the trainee-flow doc's point #6, where proctoring violations never reach the backend — here it's worse, since even the data driving the trainer's lock UI isn't real). TopPerformersCard is likewise called with no performers prop, so despite data.topPerformers being real (computed server-side from AssessmentResult), the card always shows five hardcoded demo names.

6. Trainee management by trainer/admin
new_trainee.tsx → useNewTraineeForm.ts collects corporate mapping, leadership context, trainee profile, contact info, and employment details, plus a client-generated System Access password (generatePassword(), a predictable TRN####@year pattern) → registerNewTrainee() in trainee.ts → POST /admin/trainees → training.py:register_trainee_admin, which checks for a clash on phone/email/username/traineeUid and inserts a Trainee row with status="Pending" — this is the admin/trainer-side registration path, distinct from the trainee's own self-registration covered above. trainee_list.tsx → fetchTraineeList() → GET /admin/trainees → training.py:list_trainees_admin returns every trainee in the system (not scoped to the current trainer), which is real, live data. Its "edit" action, though, just routes to /session_dashboard with no conferenceUid param — falling straight into the hardcoded CONF25456581 fallback from section 5 — rather than to any trainee-edit screen; there's no trainee-edit UI actually built.

7. Attendance lists
attendance_list.tsx, confirmed_attendance.tsx, and pending_attendance.tsx all share the AttendanceListView component and all call fetchAttendanceList() in api/attendanceList.ts, which hits GET /admin/attendance. That endpoint does not exist anywhere in the backend — attendance.py only exposes /attendance/check-in, /verify-location, and /check-in/secure (all trainee-facing), and training.py has no GET /admin/attendance route. All three screens will error against the real backend, land in their catch block, and silently render an empty state; confirmed_attendance.tsx and pending_attendance.tsx only differ from attendance_list.tsx by an extra client-side .filter(item => item.marked / !item.marked) applied to a response that never arrives. This whole trio is non-functional right now, not just running on fallback data.

8. Session report
session_report.tsx falls back to the same hardcoded conferenceUid = "CONF25456581" when no param is passed. It does call the real fetchSessionDashboard() → GET /admin/trainings/{uid} for the summary header (session name/date pulled from data.trainingType/data.conferenceDate), but the two DataTable grids beneath it — "Quiz Participant Details" and "Test Participant Details" — are both bound to the same static DEMO_SESSION_REPORT_PARTICIPANTS import from data/mockData.ts and never touch data.trainees or data.topPerformers from the live response, so the report looks populated but shows identical canned rows regardless of which session it's opened for.

9. Trainer profile
trainer_profile.tsx → useTrainerProfileForm.ts → fetchTrainerProfile()/updateTrainerProfile() in api/trainerProfile.ts → GET/PATCH /admin/profile. That route doesn't exist on the backend either — admin.py only has POST /admin/login and trainer.py only has GET /admin/trainers[/{username}]; there is no profile router at all. useTrainerProfileForm's load() has no catch around the fetch, so the request rejects, profile stays null, loading is still forced to false in the finally block, and the screen renders its section components against a null form.profile. This screen is entirely non-functional against the real backend, another orphaned frontend/backend pairing alongside the attendance lists.

Biggest issues, if you want to tackle any next: the live session dashboard's fakery (#5) is the most consequential — it's the core "run a session" feature, and unlike a missing feature this is worse because the backend work already exists and simply isn't wired up (markAttendance/resetAttendance, the real trainees list, the real topPerformers) while the proctoring lock/unlock UI operates on entirely fabricated per-trainee data with no backend concept behind it at all. Close behind: the two orphaned endpoints, GET /admin/attendance (#7, three dead screens) and GET/PATCH /admin/profile (#9, one dead screen) — both need either a new backend route or rewiring to something that already exists. After that, the hardcoded CONF25456581 fallback shared by session_dashboard.tsx and session_report.tsx is a smaller but recurring footgun (same pattern as the trainee flow's hardcoded demo-trainer ID) that will silently mask a broken navigation param. Lowest priority: the session report's canned participant tables (#8) and trainee_list's edit button routing nowhere useful (#6) are cosmetic gaps rather than broken transactions.
